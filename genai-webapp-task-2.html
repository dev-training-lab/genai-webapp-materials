このタスクのゴール

  1. 作業を始める前に、Issue に「何を・どこまで」を書いてから AI に頼む
  2. 設計の判断を ADR に残し、人にも AI にも「なぜそうしたか」が伝わる状態にする
  3. AI の作業環境（ハーネス）を整え、AI が自分の変更を自分で検証できるようにする
  4. 守りたいルールを、お願いではなく仕組み（ガードレール）で守る

AI への指示は、守られないことがあります。CLAUDE.md や AGENTS.md に書いたルールも、AI が読み落としたり誤解したりします。破られて困るルールは、テスト・フック・CI など機械が必ず止める形にするのがこのタスクの中心です。

4つの道具の役割

Issue何を・どこまで

作業の目的と受け入れ条件、やらないことを書く。AI への依頼の出発点で、PR とつながって「なぜこの変更をしたか」の記録になる。

置き場所：fork の Issues

ADRなぜそう決めたか

Architecture Decision Record。あとから変えにくい設計判断を、背景・選んだ案・捨てた案とともに1件1ファイルで残す。

置き場所：docs/adr/

ハーネスAI の作業環境

AI が正しく働くための足場。指示ファイル、ひと言で回せる検証コマンド、完了の定義、ツールの権限設定など。

置き場所：CLAUDE.md / AGENTS.md、各ツールの設定

ガードレールはみ出したら止める

ルール違反を機械的に検出して止める仕組み。人が書いても AI が書いても同じように効く。

置き場所：テスト、git フック、CI

守りたいことを、どこに書くか

同じルールを「指示」と「仕組み」の両方に書くのが基本です。指示は AI が最初から正しく書くため、仕組みは間違えたときに止めるためにあります。

守りたいこと指示（CLAUDE.md / AGENTS.md）仕組み（ガードレール）
コードの書式をそろえる—Spotless（./gradlew check で検出）
Controller から Mapper を直接呼ばないレイヤーの規約として書くArchUnit のテスト
適用済みのマイグレーションを編集しない規約として書くpre-commit フック ＋ CI
テストが通らない変更をマージしない「check が通るまで完了にしない」と書くCI（通るまでマージしない）
秘密情報を読ませない・コミットしない書くgitleaks（pre-commit フック ＋ CI）、.gitignore、Claude Code の deny 設定

開発の流れ 1つの機能をこの順で回す

  1. Issue を書く目的・受け入れ条件・範囲外
  2. ADR を書く設計の判断があるときだけ
  3. ブランチを切るfeature/12-reservation
  4. AI と実装計画 → 実装 → AI 自身が検証
  5. ガードレールpre-commit とテストで止まる
  6. PR を出すCloses #12 と ADR へのリンク
  7. CI とレビュー通ったら fork の main へマージ
  8. 振り返る同じ失敗は仕組みに還元
作業はすべて自分の fork の中で行います。Issue も PR も fork 側に作り、fork の main へマージします。本家（dev-training-lab/genai-webapp-starter）へマージすることはありません。
進捗は本家への Draft PR で共有します。前編で作った「進捗」Draft PR は fork の main を指しているので、fork でマージするたびに自動で更新されます。

ADR（設計判断の記録）

書くとき

  • 複数の案で迷い、どれかを選んだ
  • あとから変えるのが大変（DB 設計、認証方式、ライブラリの採用など）
  • レビューで「なぜこうしたの？」と聞かれそう

書き方のルール

  • 1つの判断につき1ファイル。docs/adr/0002-use-mybatis.md のように連番を振る
  • 捨てた案と理由も書く（AI が同じ案を何度も提案するのを防げる）
  • 「採用」にしたあとは書き換えない。判断を変えるときは新しい ADR を書き、古い方の状態を「置き換え済み」にする

テンプレート（例：前編の判断を後から記録したもの）

docs/adr/0002-use-mybatis.md
# 0002. DB アクセスに MyBatis を使う

- 状態: 採用
- 日付: YYYY-MM-DD
- 関連: #3

## 背景
検索条件が変わる一覧検索や、月別の集計がある。
SQL を自分で書いて読める状態にしたい。

## 決定
DB アクセスには MyBatis を使い、SQL は Mapper の XML に書く。
Controller から Mapper を直接呼ばず、必ず Service を経由する。

## 検討した案
- Spring Data JPA: 単純な CRUD は楽だが、発行される SQL が見えにくい。採用しない
- JPA と MyBatis の併用: 同じトランザクション内で更新が見えない問題が起きやすい。採用しない

## 影響
- SQL を書く量は増えるが、実行される SQL をレビューで確認できる
- レイヤーの決まりは ArchUnit のテストで守る

最初の週に、前編で決めたことを後から ADR にします（例：0001 ADR を使う、0002 MyBatis を使う、0003 フロントから API への接続方式）。決めた理由を思い出せないものは、AI に当時のコードを読ませて下書きさせ、自分で直してください。

Issue と PR

最初に fork の Issues を有効にしてください。fork では Issues が無効になっています。fork の Settings → General → Features で Issues にチェックを入れます。

Issue の書き方

雛形の .github/ISSUE_TEMPLATE/task.yml により、Issue 作成画面に次の項目が出ます。

項目書くことよくない例 → よい例
背景・目的なぜ必要か「予約機能」→「貸出中の本を、返却後すぐ借りられるよう順番待ちしたい」
受け入れ条件完了を確認できるチェックリスト「予約できる」→「貸出中の備品だけ予約できる」「同じ人は同じ備品を二重に予約できない」
範囲外今回やらないこと「予約者への通知メールは送らない」
関連する ADR従うべき設計判断docs/adr/0002-use-mybatis.md

1 Issue ＝ 1 ブランチ ＝ 1 PR。1つの PR で読みきれない大きさなら、Issue を分けます。AI に一度に頼む量も、この単位に収めます。

PR の書き方

雛形の .github/pull_request_template.md が PR の説明欄に入ります。Closes #12 と書いておくと、main へマージしたときに Issue が自動で閉じます。

ハーネス（AI の作業環境）を整える

AI は、渡された情報と使えるコマンドの範囲でしか働けません。前編で作った CLAUDE.md / AGENTS.md に、どこを読むか・どう確かめるか・いつ完了かを書き足します。

CLAUDE.md / AGENTS.md に追記する例
# 作業の進め方
- 着手する前に、対象の Issue と docs/adr/ を読む
- ADR の決定に反する変更が必要なときは、実装せずに理由と代案を示す
- 設計の判断をしたら、docs/adr/ に ADR の下書きを追加する
- git push はしない（push は人が行う）

# 完了の定義
次がすべて通るまで「完了」と報告しない。通らなかったときは、失敗の内容をそのまま報告する。
- バックエンド: cd backend && ./gradlew check
- フロントエンド: cd frontend && npm run lint && npm run build

# 守ること（違反はテストとフックでも検出される）
- Controller から Mapper を直接呼ばない（ADR-0002）
- 適用済みのマイグレーションは編集しない
- 書式は ./gradlew spotlessApply でそろえる

ツールごとの設定

ツール設定すること
Claude Code.claude/settings.json で読ませないファイルや実行させないコマンドを指定し、リポジトリにコミットする。慣れてきたら hooks で、ファイル編集のたびにチェックを自動実行することもできる
Codexアプリのアクセス権は、承認を求める設定から始める。慣れてきたら .codex/ にコマンドのルールや hooks を置ける（信頼済みのプロジェクトでだけ読み込まれる）

ガードレールを入れる 手元で止め、CI でも止める

1テストSpotless と ArchUnit を ./gradlew check に組み込む
2pre-commit フック秘密情報・マイグレーション・書式を、コミットする前に手元で止める
3CIPR ごとに同じチェックを GitHub で実行する
4マージのルールCI が通らない PR は main へマージしない

① Spotless と ArchUnit

backend/build.gradle（追加する部分）
plugins {
    // 既存のプラグインに追加
    id 'com.diffplug.spotless' version '8.12.0'
}

dependencies {
    // 既存の依存関係に追加
    testImplementation 'com.tngtech.archunit:archunit-junit5:1.5.1'
}

spotless {
    java {
        googleJavaFormat()
        removeUnusedImports()
    }
}
backend/src/test/java/com/example/app/ArchitectureTest.java
package com.example.app;

import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses;

import com.tngtech.archunit.core.importer.ImportOption;
import com.tngtech.archunit.junit.AnalyzeClasses;
import com.tngtech.archunit.junit.ArchTest;
import com.tngtech.archunit.lang.ArchRule;

@AnalyzeClasses(packages = "com.example.app", importOptions = ImportOption.DoNotIncludeTests.class)
class ArchitectureTest {

  @ArchTest
  static final ArchRule controllerDoesNotUseMapper =
      noClasses()
          .that()
          .resideInAPackage("..controller..")
          .should()
          .dependOnClassesThat()
          .resideInAPackage("..mapper..")
          .because("DB アクセスは Service を経由する（ADR-0002）");

  @ArchTest
  static final ArchRule serviceDoesNotUseController =
      noClasses()
          .that()
          .resideInAPackage("..service..")
          .should()
          .dependOnClassesThat()
          .resideInAPackage("..controller..");
}

書式が崩れていると ./gradlew check が失敗し、./gradlew spotlessApply で自動修正できます。.because(...) に ADR の番号を書いておくと、違反したときに AI も人も理由をたどれます。

② pre-commit フック

.githooks/pre-commit
#!/bin/sh
# 秘密情報（API キーやパスワードなど）が含まれていないかを調べる
if command -v gitleaks >/dev/null 2>&1; then
  gitleaks git --pre-commit --staged --redact --no-banner . || {
    echo "秘密情報らしき文字列が見つかりました。該当する行をコミットから外してください" >&2
    exit 1
  }
else
  echo "gitleaks が見つからないため、秘密情報のチェックを飛ばしました（CI では実行されます）" >&2
fi

# 適用済み（コミット済み）のマイグレーションの変更・削除・名前変更を止める
changed=$(git diff --cached --name-only --diff-filter=MDR -- backend/src/main/resources/db/migration/)
if [ -n "$changed" ]; then
  echo "適用済みのマイグレーションは変更できません。新しい V*__*.sql を追加してください:" >&2
  echo "$changed" >&2
  exit 1
fi

# バックエンドに変更があるときだけ書式をチェックする
if git diff --cached --name-only | grep -q '^backend/'; then
  (cd backend && ./gradlew -q spotlessCheck) || {
    echo "書式が崩れています。cd backend && ./gradlew spotlessApply を実行してください" >&2
    exit 1
  }
fi

秘密情報のチェックには gitleaks を使います。macOS なら brew install gitleaks、Windows なら公式の Releases から入手してください。入っていない場合、フックは警告を出して先に進み、CI で止まります。

フックを有効にする（clone するたびに1回）
chmod +x .githooks/pre-commit
git config core.hooksPath .githooks

フックは git commit --no-verify で飛ばせます。そのため、同じチェックを CI でも必ず行います。AI がフックを飛ばしてコミットしようとしたら、止めて理由を確認してください。

③ CI（GitHub Actions）

.github/workflows/ci.yml
name: CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  backend:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_DB: app
          POSTGRES_USER: app
          POSTGRES_PASSWORD: app
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U app"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '25'
          cache: gradle
      - run: ./gradlew check

  frontend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: lts/*
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - run: npm ci
      - run: npm run lint
      - run: npm run build

  migration-guard:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - name: 適用済みマイグレーションの変更を検出
        env:
          BASE_REF: ${{ github.base_ref }}
        run: |
          changed=$(git diff --name-only --diff-filter=MDR "origin/$BASE_REF...HEAD" -- backend/src/main/resources/db/migration/)
          if [ -n "$changed" ]; then
            echo "::error::適用済みのマイグレーションが変更されています: $changed"
            exit 1
          fi

  secret-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - name: 秘密情報のチェック
        run: docker run --rm -v "$PWD:/repo" -w /repo zricethezav/gitleaks:v8.30.1 git --redact --no-banner .
fork の Actions を確認してください。ワークフローを追加したら fork の Actions タブを開き、止まっていれば有効にします。fork は Private なので、実行時間は自分のアカウントの無料枠から使われます。CI は PR と main への push のときだけ動かし、無駄に回さないようにしましょう。

④ マージのルール

無料プランの Private リポジトリでは、「CI が通らないとマージできない」設定（ブランチ保護）を使えない場合があります。そのため、次を自分のルールとして守ります。

  • main へは直接 push せず、必ず PR を通す
  • CI が緑になってからマージする。赤いままマージしない
  • AI に「マージして」と頼まない。マージは自分の目で CI を確かめてから行う

fork の Settings → Branches でブランチ保護を設定できる場合は、PR とステータスチェックを必須にしておくと確実です。

効いているかを確かめる

入れただけでは、本当に止まるか分かりません。わざと違反して、止まることを確かめてから ai-log に記録します。

わざとやること止まる場所
Controller で Mapper を直接使う./gradlew check（ArchUnit）、CI
インデントを崩す・使っていない import を残すpre-commit フック、CI
V1__init.sql を書き換えてコミットするpre-commit フック
AI に作らせたダミーの API キーを書いてコミットする（本物は絶対に使わない）pre-commit フック（gitleaks）、CI（secret-scan）
同じ変更を --no-verify でコミットし、PR を出すCI（migration-guard）

進め方 チェックは このブラウザに保存されます
